## 第1群: プロンプトの4要素（作問 1〜2問）

### 論点A1: プロンプトの4要素の定義
- **論点**: Instruction、Context、Input Data、Output Indicator
- **章**: 第5章
- **事実**: DAIR.AI の Prompt Engineering Guide は、プロンプトの要素を次の4つとして定義している。Instruction は「モデルに実行してほしい特定のタスクまたは命令」、Context は「外部情報や追加の文脈（モデルをより良い応答に導く）」、Input Data は「応答を見つけたい入力または質問」、Output Indicator は「出力のタイプや形式を示す」もの。日本語版は Instruction=命令、Context=文脈、Input data=入力データ、Output indicator=出力指示子と訳している。
- **出典**:
  - 英語版 https://www.promptingguide.ai/introduction/elements （本文確認、確認日 2026-10-15）
  - 日本語版 https://www.promptingguide.ai/jp/introduction/elements （本文確認、確認日 2026-10-15）
- **確度**: 高（一次情報で確認）。作問可。
- **出題の狙い**:
  - 問い方案: 「プロンプトの4要素のうち、出力のタイプや形式を示すものはどれ？」（正解 Output Indicator）。または逆に「『応答を見つけたい入力や質問』にあたるものはどれ？」（正解 Input Data）。
  - 紛らわしい誤答: Input Data と Context（どちらも「情報」を与えるように見える）、Instruction と Output Indicator（どちらも「〜してください」の文に見える）、Zero-Shot（手法名で要素ではない）。
  - 注意: 日本語の訳語は「命令/指示」「文脈/コンテキスト」などゆれる。シラバスは英語表記（Instruction 等）なので、選択肢は英語表記にそろえ、必要なら括弧で日本語を添えるのがよい。
  - 注意: 「4要素」は DAIR.AI のガイドでの整理。「公式規格」と言い切らない。問題文は「プロンプトの要素として整理される」程度にする。

### 論点A2: 具体的なプロンプトのどの部分がどの要素か／要素はすべて必須ではない
- **論点**: 4要素の見分け方、Context の有無
- **章**: 第5章
- **事実**: 同ガイドの分類タスクの例は、次のとおり。「Classify the text into neutral, negative, or positive / Text: I think the food was okay. / Sentiment:」。ここで Instruction は分類を指示する文、Input Data は分類対象の文（Text: 以下）、Output Indicator は末尾の「Sentiment:」。この例には Context は含まれない。また日本語版は「すべてのコンポーネントが必要なわけではなく、フォーマットは手元のタスクに依存します」と述べている。
- **出典**:
  - https://www.promptingguide.ai/introduction/elements （英語版、例の部分を確認、確認日 2026-10-15）
  - https://www.promptingguide.ai/jp/introduction/elements （日本語版。「すべてのコンポーネントが必要なわけではない」の記述を確認。ただし日本語版には具体例が載っていない。確認日 2026-10-15）
  - 日本語の例文（テキスト分類）: https://www.promptingguide.ai/jp/introduction/examples （「テキストをneutral、negative、またはpositiveに分類してください。」の指示文を確認、確認日 2026-10-15）
- **確度**: 高。ただし、具体的な日本語プロンプト文を4要素に振り分ける作業は、定義に当てはめた作問側の解釈になる。定義（A1）から一意に決まる例文だけを使うこと。
- **出題の狙い**:
  - 問い方案（例）: 「次のプロンプトで、『以下の文章を3行で要約してください』にあたる要素はどれ？ 『【文章】…』は入力データ」のように、1つの要素だけを問い、他の要素は文に明記する。
  - 紛らわしい誤答: Context（背景情報）と Input Data（処理の対象）。「あなたは編集者です。読者は初心者です」は Context とも Instruction とも読めてしまうので、例文には使わない（好みで答えが分かれる）。出力形式を示す部分（「表形式で」「箇条書きで3つ」）は Output Indicator に当てはまり、見分けやすい。
  - 「すべての要素が必要」という誤答を作る場合は、日本語版の記述が根拠になる。

## 第2群: n-gramモデルとニューラル言語モデル（作問 1問）

### 論点B1: n-gramモデルの仕組み（直前の語だけを手がかりに確率を求める／データ不足の問題）
- **論点**: n-gramモデル
- **章**: 第5章
- **事実**: 教科書 Dive into Deep Learning（d2l.ai）は、次のトークンの確率を直前のいくつかのトークンだけで近似するマルコフ性を説明している。1つ前だけを使う場合を1次、より長い履歴を使うほど高次になる。そして、1つ・2つ・3つの変数を使う式を、それぞれ unigram、bigram、trigram モデルと呼ぶ。さらに「データに現れない、もっともらしい3語の組み合わせが多数ある」という疎（そ）なデータの問題があり、対策のラプラス平滑化（すべての頻度に小さな定数を足す）も説明している。n-gramでは出現頻度の数え上げで確率を推定し、すべての頻度を保存する必要があることも述べている。
- **出典**: https://d2l.ai/chapter_recurrent-neural-networks/language-model.html （本文確認、確認日 2026-10-15）
- **確度**: 高（d2l.ai で確認）。ただし「n-gramは直前の n−1 語から次の語を予測する」という言い方そのものは、読めた本文では「1語・2語・3語を条件にする unigram/bigram/trigram」から導かれる説明である。次の補強資料は、PDFで本文を読み込めなかったため未確認:
  - Jurafsky & Martin "Speech and Language Processing" 第3章（https://web.stanford.edu/~jurafsky/slp3/3.pdf）: PDFが読めず、本文未確認。
  - プリンストン大 COS 484 講義資料 lec2.pdf、コーネル大 CS4740 Lec2.pdf: PDFが読めず、本文未確認。
  - したがって「n−1語」の厳密な言い方は、問題文では「直前の数語（n−1語）」程度にとどめるか、Jurafsky の本文を人が確認してから使う。
- **出題の狙い**:
  - 問い方案: 「n-gramモデルが次の単語の確率を求めるときの手がかりとして正しいものはどれ？」正解「直前の数語だけ（直前のn−1語）」。
  - 紛らわしい誤答: 「文章全体を一度に見て」（Transformerの特徴と混同）、「単語の意味を数値ベクトルで表して」（ニューラル言語モデルの特徴）、「ランダムに選んで」。
  - 「n-gramは統計（頻度の数え上げ）に基づく」という点が、ニューラル言語モデルとの対比に使える。

### 論点B2: ニューラル言語モデル（Bengio et al. 2003）はn-gramとどう違うか
- **論点**: ニューラル言語モデル
- **章**: 第5章
- **事実**: Bengio らの論文 "A Neural Probabilistic Language Model"（Journal of Machine Learning Research 3, 2003）は、言語モデルの難しさを「次元の呪い」（テスト時の単語列が学習データに現れた列と異なりやすいこと）だとしている。従来のn-gramは、学習データ中の短い重なった単語列を組み合わせて対処する。これに対して著者らは、単語の分散表現を学習し、似た単語に似た表現を持たせることで、見たことのない単語列にも汎化できるようにした。2つのコーパスで、当時の最先端のn-gramモデルを上回り、より長い文脈も使えたと述べている。
- **出典**: https://jmlr.org/papers/v3/bengio03a.html （要旨ページを確認、確認日 2026-10-15）。論文PDF https://www.jmlr.org/papers/volume3/bengio03a/bengio03a.pdf は本文を読み込めず、本文は未確認（要旨のみ）。
- **確度**: 高（要旨ページで確認）。ただし「要旨のみ確認」なので、論文本文の細部（モデル構造、パラメータ数）は問わない。
- **出題の狙い**:
  - 問い方案: 「ニューラル言語モデルがn-gramモデルと比べて持つ利点として適切なものはどれ？」正解「単語を意味の近さを反映したベクトル（分散表現）で表すので、学習データに現れなかった単語列にも対応しやすい」。
  - 紛らわしい誤答: 「出現頻度を数えるだけで済むので学習が速い」（n-gramの特徴）、「必ず人間より正確」。
  - 年（2003年）は覚えさせる必要はない。年を問うなら論文名と出典に一致させる。ニューラルネットワークは「必ず優れる」と言い切らず、論文が示す比較の範囲（2つのコーパス）にとどめる。
  - n-gram の B1 と B2 は同じ1問にまとめる（作問は1問）。B1 で仕組み、B2 で対比、のどちらかを選ぶ。

## 第3群: テキスト生成AIの不得意なこと（作問 2問）

共通の注意: 「LLM単体では」という条件を問題文に入れる。外部ツール（コード実行、検索）を併用した場合は別の話にする。モデルの具体名やカットオフの日付は問わない（変わりやすいため）。

### 論点C1: 正確な文字数の指定・数え上げが苦手な理由（トークン単位の処理）
- **論点**: 正確な文字数の指定
- **章**: 第5章
- **事実**: OpenAI の API ドキュメントは、テキスト生成と埋め込みのモデルは、トークンというかたまりでテキストを処理すると説明している。トークンは「よく現れる文字の並び」を表し、例として " tokenization" は " token" と "ization" に分かれる。Google の Gemini API ドキュメントも、トークンは1文字（z）のこともあれば単語全体（cat）のこともあり、英語では約4文字が1トークンの目安だと述べている。つまりモデルは文字単位ではなくトークン単位で処理する。研究では、byte-level BPE のトークナイザが、文字などの数え上げの性能に影響することが論じられている（Zhang, Cao, You 2024）。
- **出典**:
  - https://developers.openai.com/api/docs/concepts （本文確認、確認日 2026-10-15）
  - https://ai.google.dev/gemini-api/docs/tokens （本文確認、確認日 2026-10-15）
  - https://arxiv.org/abs/2410.19730 （Counting Ability of Large Language Models and Impact of Tokenization、要旨を確認、確認日 2026-10-15）
- **確度**: 高。ただし次の点は言い切らない:
  - 「文字数を数えられないのはトークン単位で処理するせいだ」という因果の断定は、一次情報では確認できていない。上記の論文はトークナイザが影響することを論じるが、検索で見つかった別の研究には「原因は計算そのものの難しさ」とする見方もある（二次的な要約で、原論文は未確認）。作問では「トークン単位で処理するため、文字数を正確に数えることが苦手とされる」「要因の1つ」の言い方にとどめる。
  - OpenAI の公式ヘルプ記事（https://help.openai.com/en/articles/4936856-what-are-tokens-and-how-to-count-them）は403で読めなかった。
- **出題の狙い**:
  - 問い方案: 「LLM単体では、『ちょうど200字で書いて』という指示を正確に守るのが苦手とされる。その理由として適切なものはどれ？」正解「テキストを文字ではなくトークンという単位で処理するため」。
  - 紛らわしい誤答: 「日本語に対応していないため」「長い文章は書けないため」「文字数のルールを学習していないため」。
  - 既存の g2-07（トークンとは何か）と重ならないよう、トークンの定義ではなく「文字数指定が苦手」を問う。
  - 「ちょうど」「正確な」という語を問題文に入れる（シラバスの『正確な文字数の指定』）。だいたいの長さの指定が効かない、とは言わない。

### 論点C2: 計算が苦手とされる／外部ツール（コード実行など）で補える
- **論点**: 計算
- **章**: 第5章
- **事実**: Toolformer の論文（Schick ら、Meta AI、2023年2月）は、言語モデルは新しいタスクを少数の例や指示から解ける一方で、「算術や事実の検索といった基本的な機能が苦手」だと述べ、電卓や検索エンジンなどのAPIをモデルが自分で呼び出す方法を提案した。Anthropic の Claude のコード実行ツールのドキュメントは、Claude がデータ分析や複雑な計算などを、サンドボックス環境で実行したコードで行えると説明している。
- **出典**:
  - https://arxiv.org/abs/2302.04761 （Toolformer、要旨を確認、確認日 2026-10-15）
  - https://platform.claude.com/docs/en/agents-and-tools/tool-use/code-execution-tool （冒頭の説明を確認、確認日 2026-10-15）
- **確度**: 高。ただし限定つき:
  - Toolformer の指摘は2023年時点のモデルについて。現在のモデルが計算でどの程度誤るかは、この調査では確認していない。「現在のLLMは計算を必ず間違える」とは言い切らない。「誤ることがある」「苦手とされる」にとどめる。
  - 「確率的な次トークン予測で計算するから誤る」という説明の一次情報は確認できていない。理由を問う問題にはしない。ツールで補える、という対処のほうを問う。
- **出題の狙い**:
  - 問い方案: 「LLM単体では計算ミスが起きることがある。この弱点を補う方法として適切なものはどれ？」正解「コード実行などの外部ツールを使って計算させ、結果を確認する」。
  - 紛らわしい誤答: 「温度（Temperature）を上げる」（ランダム性が増えて逆効果）、「プロンプトを長くする」、「文字数を指定する」。
  - g5-06（Temperature）、g5-03（Chain-of-Thought）と混同させない。CoT は精度向上の手法として別問題で出題済み。

### 論点C3: 最新の情報（知識カットオフ）／検索で補える
- **論点**: 最新の情報
- **章**: 第5章
- **事実**: Anthropic の Models overview は、「Reliable knowledge cutoff」を「モデルの知識がもっとも豊富で信頼できる日付」、「Training data cutoff」をより広い学習データの範囲と定義している。Claude の Web 検索ツールのドキュメントは、このツールで Claude が「知識カットオフを超えた最新の情報」で答えられると説明している。Google の Gemini API の Google 検索によるグラウンディングも、リアルタイムのウェブ情報につなぐことで、知識カットオフを超えた、出典つきの回答を可能にすると説明している。
- **出典**:
  - https://platform.claude.com/docs/en/models/overview （定義を確認、確認日 2026-10-15）
  - https://platform.claude.com/docs/en/agents-and-tools/tool-use/web-search-tool （冒頭を確認、確認日 2026-10-15）
  - https://ai.google.dev/gemini-api/docs/google-search （冒頭を確認、確認日 2026-10-15）
- **確度**: 高。ただし限定つき:
  - カットオフの具体的な日付、各社の機能名、提供範囲は変わりやすいので問わない（CLAUDE.md の方針）。
  - OpenAI 側の knowledge cutoff の説明、GPT-4 技術報告書の「事前学習データ以降の出来事の知識を欠く」旨の記述は、読めなかったため未確認（https://openai.com/index/gpt-4-research/ は403。arXiv の要旨ページ https://arxiv.org/abs/2303.08774 には該当記述なし）。
- **出題の狙い**:
  - 問い方案: 「LLM単体では、学習データの時点より後の出来事を答えるのが苦手とされる。これを補う方法として適切なものはどれ？」正解「Web検索などの外部ツールと組み合わせる」。または「生成AIが『最新の情報』を苦手とする理由」で正解「学習に使ったデータの時点より後の情報を持たないため」。
  - 紛らわしい誤答: 「パラメータ数を増やす」「Temperature を下げる」「Top-p を上げる」（設定では最新情報は得られない）。
  - 既存の g2-20（コンテキストウィンドウ）や、RAG の問題と混同しない。RAG（検索拡張生成）は別章で出題済みなので、本問は「検索ツールを併用」程度にとどめる。

## 第4群: 業務シナリオ型（作問 2〜3問）

### 論点D1: 「姓と名の分離」など出力形式を指定する部分は Output Indicator
- **論点**: 姓と名の分離／出力形式の指定（4要素との結びつけ）
- **章**: 第5章
- **事実**: Output Indicator は「出力のタイプや形式を示す」要素である（A1）。Anthropic のプロンプトのベストプラクティスは、「望む出力形式と制約を具体的に書く」ことを勧めている。Prompt Engineering Guide も「例を示すことは、特定の形式の出力を得るのにとても有効」と述べている。これらを合わせると、「姓と名を『,』で区切って1行ずつ出力」のように出力の形を指示する部分は Output Indicator にあたる。
- **出典**:
  - https://www.promptingguide.ai/introduction/elements （確認日 2026-10-15）
  - https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices （「Be specific about the desired output format and constraints.」を確認、確認日 2026-10-15）
  - https://www.promptingguide.ai/introduction/tips （確認日 2026-10-15）
- **確度**: 高（個々の事実は一次情報で確認）。ただし「姓名分離の出力形式指定＝Output Indicator」という当てはめは、定義からの導出で、公式にそう書かれているわけではない。問題文に区切り文字や列を明記して「形式を示す部分」と問えば、解釈の余地は小さい。
- **出題の狙い**:
  - 問い方案: 「『次の氏名を姓と名に分け、「姓,名」の形式で1行ずつ出力してください。【氏名一覧】』というプロンプトで、『「姓,名」の形式で1行ずつ出力』の部分にあたる要素はどれ？」正解 Output Indicator。
  - 紛らわしい誤答: Instruction（「分けてください」の部分）、Input Data（氏名一覧）、Context。
  - g5-08（出力形式の指定は『どの工夫』）と近い。g5-08 は「工夫」の名称を問う問題なので、本問は4要素の名称で問うと区別できる。
  - 「氏名の姓名分離はLLMが正しく分けられる」とは言わない。外国人名や複姓などで誤りうるが、これを裏付ける一次情報は確認できていない（未確認）。

### 論点D2: 出力形式をそろえたいときは、入力と出力の例を示す（Few-Shot）
- **論点**: Few-Shot プロンプティング（ふりがな・姓名分離などの書式をそろえる場面）
- **章**: 第5章
- **事実**: Anthropic のプロンプトのベストプラクティスは、例は「出力の形式、トーン、構造を整える最も信頼できる方法の1つ」で、少数の例（few-shot）は正確さと一貫性を高めると述べている。Google の Gemini API のドキュメントは「プロンプトには常にfew-shotの例を含めること」を勧め、例の構造と書式をそろえることを求めている（例が多すぎると過学習の恐れがあるとも注意）。OpenAI のドキュメントも、Few-shot を、少数の入力と出力の例をプロンプトに含めて導く方法と説明している。
- **出典**:
  - https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices （Use examples effectively、確認日 2026-10-15）
  - https://ai.google.dev/gemini-api/docs/prompting-strategies （確認日 2026-10-15）
  - https://developers.openai.com/api/docs/guides/prompt-engineering （確認日 2026-10-15）
- **確度**: 高。ただし、各社の細かい推奨（例の数「3〜5個」など）は変わりうるので問わない。
- **出題の狙い**:
  - 問い方案: 「住所から都道府県だけを決まった書式で取り出させたい。出力の書式をそろえるのに有効な方法はどれ？」正解「入力と出力の例を数個示す（Few-Shot）」。
  - 紛らわしい誤答: Zero-Shot（例を示さない）、Temperature を上げる、Chain-of-Thought（推論過程を出力させる手法）。
  - g5-02（Few-shot の定義）と同じ問いにならないよう、定義を問うのではなく業務シナリオで手法を選ばせる。重複リスクがあるため、作問時は g5-02 の選択肢と並べて確認すること。

### 論点D3: アンケート分析・ふりがななどの出力は人が確認する（ハルシネーションは完全には防げない）
- **論点**: アンケートの分析、ふりがなの記載（注意点）
- **章**: 第5章
- **事実**: Anthropic の「Reduce hallucinations」ガイドは、Claude のような高性能な言語モデルでも、事実と異なる内容や、与えた文脈と矛盾する内容を生成することがあるとし、「これらの手法はハルシネーションを大きく減らすが、完全には消せない。重要な情報は必ず確認すること」と述べている。軽減策の例は、「分からない」と答えることを許す、文書から引用を先に抜き出して根拠にする、各主張に出典の引用をつけさせる、など。総務省の令和6年版情報通信白書も、生成AIの出力にもっともらしい誤りが含まれうること（ハルシネーション）を課題として挙げている。
- **出典**:
  - https://platform.claude.com/docs/en/test-and-evaluate/strengthen-guardrails/reduce-hallucinations （本文確認、確認日 2026-10-15）
  - https://www.soumu.go.jp/johotsusintokei/whitepaper/ja/r06/html/nd141100.html （確認日 2026-10-15。ただし取得した本文に文字化けがあり、引用の細部は要再確認。このページだけを根拠にしない）
- **確度**:
  - 「重要な情報は確認が必要」「ハルシネーションは完全には防げない」: 高（Anthropic の公式ガイドで確認）。作問可。
  - 「アンケートの自由記述の分析で、人が確認すべき点」: 一次情報での直接の記述は見つからなかった。ハルシネーション一般の注意としてなら問える（作問可）が、「分類の数や代表的な意見の抜き出しが正しいか」といった具体策を正解にするのは、一次情報がないため作問不可。
  - 「ふりがな・人名の読みはLLMが誤りやすい」: 一次情報を確認できなかった（未確認）。作問不可。日本語の官公庁・自治体ガイドライン（大分市、東京都、総務省の各PDF）は本文を読み込めなかったため、記述の有無自体が不明。
- **出題の狙い**:
  - 問い方案: 「生成AIにアンケートの自由記述を要約・分類させた。業務で使う前にすべきこととして最も適切なものはどれ？」正解「元の回答と照らして、要約や分類が合っているかを人が確認する」。
  - 紛らわしい誤答: 「Temperature を上げれば誤りがなくなる」「生成AIの出力はそのまま報告してよい」「文字数だけ確認する」（g5-07 の誤答に近いので、同じ誤答を使い回さない）。
  - g5-07（生成AIの文章を業務で使う前に行うべきこと）と問いがほぼ同じになる危険が高い。アンケート分析にするなら「元データと突き合わせる」を正解にし、g5-07 の正解（事実確認）と区別がつくようにする。重複と判断されたら、この論点は使わない（C1〜C3 と D1・D2 だけで7問を構成できる）。

### 論点D4: 入力データ（要約したい文章など）は区切って示し、条件は具体的に書く
- **論点**: 文章の要約、Input Data
- **章**: 第5章
- **事実**: Anthropic のベストプラクティスは、指示・文脈・例・入力データが混ざるプロンプトでは、種類ごとにタグ（`<instructions>`、`<context>`、`<input>` など）で囲むと、誤解が減ると述べている。Prompt Engineering Guide は、あいまいな指示（「説明は短く、数文だけで、あまり詳しくしないで」）より、具体的な指示（「高校生向けに、プロンプトエンジニアリングを2〜3文で説明して」）のほうが良いとする。また、してはいけないことを言うより、してほしいことを言うほうがよい、とも述べている。
- **出典**:
  - https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices （Structure prompts with XML tags、確認日 2026-10-15）
  - https://www.promptingguide.ai/introduction/tips （Specificity / Avoid impreciseness、確認日 2026-10-15）
- **確度**: 高。ただし g5-05（目的・前提条件・出力形式を具体的に）と近いので、要約の業務シナリオで「どの要素が足りないか」を問う形にずらすこと。
- **出題の狙い**:
  - 問い方案: 「『次の文章を要約してください』とだけ書いたプロンプトに足すと、出力の形式が決まりやすくなる要素はどれ？」正解「Output Indicator（『3つの箇条書きで』など）」。
  - 紛らわしい誤答: Input Data（すでに文章を渡している前提なら不要）、Context。
  - 要約の対象が「大人向けか子ども向けか」のような好みで答えが分かれる出題は避ける。

## 作問への推奨配分（参考）
- 4要素: A1（定義）＋ A2（当てはめ）→ 2問まで。D1・D4 も4要素を使うため、4要素系の問題が3問を超えないよう注意。
- n-gram/ニューラル言語モデル: B1 と B2 を1問に（対比形式）。
- 不得意: C1（文字数）、C3（最新情報）の2問が、一次情報の確度が高く、理由も言いやすい。C2（計算）は理由を問わず、対処（外部ツール）を問う形ならよい。
- 業務シナリオ: D2（Few-Shot）を中心に、D1 を4要素と結びつけて使う。D3 は g5-07 と重複するので慎重に。
