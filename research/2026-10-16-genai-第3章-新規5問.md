## 分野1: データの水増し（データ拡張）

### 論点1: データ拡張の目的（学習データの多様性・量を増やす）
- **論点**: データの水増し（augmentation）、データ拡張技術
- **章**: 第3章
- **事実**: TensorFlow の公式チュートリアルは、データ拡張を「画像の回転のような、ランダムだが現実的な変換を適用して、学習セットの多様性を高める技術」と説明している。同チュートリアルは、ランダムな変換が「データセットの汎化と拡張に役立つ」とも述べる。d2l.ai は、画像拡張を「ランダムな変更を加えて、似ているが異なる学習例を作り出す」ものとし、左右反転・切り抜き・明るさ／コントラスト／彩度／色相の変更を例にあげる。
- **出典**:
  - https://www.tensorflow.org/tutorials/images/data_augmentation （確認日 2026-10-16、本文確認済み）
  - https://d2l.ai/chapter_computer-vision/image-augmentation.html （確認日 2026-10-16、本文確認済み）
- **確度**: 高（一次情報で確認）
- **出題の狙い**:
  - 問い方の案: 「学習用の画像が少ないとき、1枚の画像を回転・反転・明るさ変更などで加工して、学習データの量や多様性を増やす手法はどれ？」→ データ拡張（データの水増し）。
  - 紛らわしい誤答候補:
    - 次元削減（g1-08と同じ対比になるので、選択肢に入れるなら他の誤答も新しいものにする）。
    - 正規化（値の範囲をそろえる。シラバスのキーワード）。
    - 画像のリサイズ（大きさをそろえる前処理。シラバスのキーワード）。
    - アノテーション（ラベル付け）。
  - 注意: TensorFlow のチュートリアルは「リサイズ・リスケール」を拡張とは別の前処理層として扱っているように見えるが、その箇所は私の取得では本文で確認できなかった（検索要約のみ）。「リサイズ・正規化は拡張ではない」と言い切る解説にする場合は、再確認が必要。
  - 注意: 「過学習を防ぐ」は TensorFlow のチュートリアルでは明示確認できなかった。目的は「多様性・量を増やす」に限定し、「過学習防止」の言い切りは避ける。
  - 具体的な手法名（CutMix, Mixup など）は正解や選択肢の軸にしない。

### 論点2: データ拡張は学習用データだけに行う
- **論点**: データの水増し（augmentation）
- **章**: 第3章
- **事実**: TensorFlow の公式チュートリアルに「データ拡張は学習セットにだけ適用すべき」という注記がある。コード例も、拡張を学習用にだけ有効にし、検証用・テスト用には適用していない。d2l.ai も「通常、画像拡張は学習例にだけ適用する」と述べる。
- **出典**:
  - https://www.tensorflow.org/tutorials/images/data_augmentation （確認日 2026-10-16）
  - https://d2l.ai/chapter_computer-vision/image-augmentation.html （確認日 2026-10-16）
- **確度**: 高
- **出題の狙い**:
  - 問い方の案: 「データ拡張の使い方として適切なものはどれ？」→ 「加工した画像は学習用データに加え、評価用（テスト）データには加工をしない」。
  - 紛らわしい誤答候補: 「テストデータも同じように水増しして精度を上げる」「拡張後の画像の正解ラベルを人が全部付け直す」（後者の事実は未確認なので、誤答にする場合も解説で断定しない）。
  - 論点1と同じ問題に両方を入れず、どちらか一方を選ぶ。初学者向けには論点1が基本。

## 分野2: 音声生成AI

### 論点3: 音声合成（TTS）＝テキストから音声を作る
- **論点**: 音楽・音声生成AI、音声合成
- **章**: 第3章
- **事実**: Google Cloud の Text-to-Speech ドキュメントは「テキスト入力を音声データに変換する処理を合成（synthesis）と呼び、出力を合成音声（synthetic speech）と呼ぶ」と説明している。入力は生のテキスト、または SSML（音声合成マークアップ言語）形式のデータ。OpenAI の Audio API にも、GPT-4o mini TTS モデルにもとづく `speech` エンドポイントがあり、記事の読み上げや多言語の音声生成などに使える。
- **出典**:
  - https://docs.cloud.google.com/text-to-speech/docs/basics （確認日 2026-10-16、本文確認済み）
  - https://developers.openai.com/api/docs/guides/text-to-speech （確認日 2026-10-16、本文確認済み。旧URL platform.openai.com から301）
- **確度**: 高
- **出題の狙い**:
  - 問い方の案: 「文章を入力すると、人が話しているような音声を生成するAI技術はどれ？」→ 音声合成（TTS）。
  - 紛らわしい誤答候補: 音声認識（音声→文字。Whisper は g3 の既存問題の選択肢に登場）、超解像（画像の高解像度化）、画像キャプション生成。
  - 注意: 特定のモデル名・声の数・エンドポイントの仕様は変わりやすいので、解説や選択肢に入れない。サービス名を使うなら「2025年に発表した」等の時点を付ける必要があるが、発表年は今回一次情報で確認できていない（未確認）。サービス名に頼らない問い方を推奨。
  - 「音声認識」との向きの対比（テキスト→音声か、音声→テキストか）で正解が1つに決まる。

## 分野3: 偽情報（ディスインフォメーション）

### 論点5: 偽情報（意図的に作られたウソ）と誤情報（勘違いで拡散）の区別 ※k10-05の裏返しにしない
- **論点**: 偽情報（ディスインフォメーション）、ディープフェイク（深層偽造）技術

- **出典**: https://www.soumu.go.jp/ict-mirai/keyword/misinformation/ （確認日 2026-10-16、本文確認済み。k10-05 と同じ出典）
- **確度**: 高（定義部分のみ）
- **確認できなかったこと**:
  - 同ページには「悪意ある情報（マルインフォメーション）」の記述がない。マルインフォメーションは今回の作問に使えない。
  - 同ページには生成AI・ディープフェイクの記述がない。
  - 「生成AIが偽情報の作成に使われる」ことを述べた総務省の令和5〜7年版情報通信白書は、HTMLが文字化けし、PDFも読めなかったため、本文を確認できていない。検索の要約では、令和7年版白書やAI事業者ガイドライン第1.2版（令和8年3月31日）が、生成AIの普及で偽情報・誤情報の生成・発信リスクが増える旨を述べているとされたが、いずれも本文の未確認（作問には使わない）。
- **出題の狙い**:
  - 角度を変えた問い方の案（定義の暗記ではなく場面の分類）: 「ある人が、特定の人物を陥れる目的で、実在の人物が言っていないことを言っているように見せる偽の動画をAIで作り、SNSに投稿した。この情報は、総務省の説明で何に当たる？」→ 偽情報（ディスインフォメーション）。決め手は「危害を与える目的で意図的に作った」こと。道具（ディープフェイクなど）は決め手ではない。
  - この形なら、定義は総務省のページで確認済みの内容だけを使い、「生成AIが偽情報に使われる」を一般論として言い切る必要がない（場面を仮定として置くだけ）。

  - 避ける形: 「勘違いで広まった間違い情報は何か」（k10-05 の裏返し）。「偽情報はAIだけで作られる」といった言い切り。

## 分野4: RAGのユースケース

### 論点6: RAGが向く場面（モデルが知らない情報）とファインチューニングが向く場面（振る舞いの調整）
- **論点**: RAG、RAGのユースケース
- **章**: 第3章
- **事実**: OpenAI の「LLMの精度を最適化する」ガイドは、RAG を「タスクを解くためのドメイン固有の文脈をモデルに与える」ものとし、モデルが情報を知らない・知識が古い・社内独自のデータが必要、といった場合に向くとする。ファインチューニングは「LLMがタスクを一貫して確実に実行できるよう学習させる」ことを目的とし、出力の形式、口調・文体、期待する推論の仕方が安定しない場合に向く。ガイドは、失敗の原因を先に切り分け、知識が足りないなら RAG、知識はあるが適用が不安定ならファインチューニング、と整理している。
- **出典**: https://developers.openai.com/api/docs/guides/optimizing-llm-accuracy （確認日 2026-10-16、本文確認済み。旧URL platform.openai.com から301）
- **確度**: 高
- **出題の狙い**:
  - 問い方の案: 「次のうち、RAGではなくファインチューニングを検討するのが適しているのはどれ？」→ 「回答の口調や出力の形式を、毎回自社の決まった形にそろえたい」。誤答は、社内規程や最新の製品マニュアルをもとに答えさせたい、といった「知識を与える」場面。
  - 逆向きの問い（「RAGが向いているのはどれ？」）にすると g3-01/g3-02 に近づく。「向かない場面」を問う形にすると角度が変わる。
  - 紛らわしさの源: 「社内データを使うなら追加学習が必要」という思い込み（g3-02/g3-01 の解説と整合）。
  - 注意: 「RAGでは文体を変えられない」「ファインチューニングでは知識を入れられない」と言い切らない。出典は「向く」「適する」の範囲で述べているだけで、この言い切りは確認できていない。「〜が向く」「〜を検討する」にとどめる。
  - 注意: 両者の併用も可能（OpenAIガイドも併用に言及）なので、「どちらか一方しか使えない」の選択肢は誤答側に置ける。

### 論点7: RAGのユースケース（社内の規程・人事問い合わせなど）
- **論点**: RAGのユースケース
- **章**: 第3章
- **事実**: AWS の解説は、RAG の使い方として、組織の人事（HR）に関する質問に答えるチャットボットを例にあげ、休暇規程や従業員本人の休暇記録を検索して答える構成を示している。RAG のメリットとして、最新の研究・統計・ニュースをモデルに提供できること、出典（ソース）を示して答えられること、モデルの再学習より費用を抑えられることをあげている。
- **出典**: https://aws.amazon.com/what-is/retrieval-augmented-generation/ （確認日 2026-10-16、本文確認済み）
- **確度**: 高
- **出題の狙い**:
  - 問い方の案（場面→手法）: 「社員からの『育休の申請手順は？』といった質問に、最新の社内規程にもとづいて答えるチャットボットを作りたい。規程が頻繁に改定される場合に適した仕組みは？」→ RAG。
  - 紛らわしい誤答候補: 規程が変わるたびにモデルを一から事前学習し直す、ファインチューニングで規程を覚えさせ続ける、プロンプトに例を書くだけ（Few-shot）。
  - 注意: 出典は「最新情報の反映」「出典の提示」「再学習より低コスト」の範囲。「ハルシネーションをなくす」とは言わない（g3-02 のとおり「低減が期待できる」止まり）。
  - 論点6と同じ問題に両方入れる場合は、論点6を主、論点7は別問にしない（論点数の都合で、どちらか選ぶ）。
  - 変わりやすい情報（AWSの製品名・機能）は問題・解説に入れない。

## 分野5: ベクトルデータベース

### 論点8: ベクトルデータベースの役割＝意味の近さ（類似度）で検索する
- **論点**: ベクトルデータベース、RAG
- **章**: 第3章
- **事実**:
  - Anthropic の解説は、RAG の前処理として、文書をチャンクに分け、埋め込みモデルでベクトル（意味を符号化した数値）にし、それを「意味の近さで検索できるベクトルデータベース」に保存する、と述べる。
  - Google Cloud の Vector Search ドキュメントは、密な埋め込み（dense）は意味を表し、類似度にもとづいて結果を返すこと、疎な埋め込み（sparse）は構文を表しキーワード検索によく使われること、両方を組み合わせるハイブリッド検索もあること、を述べる。
  - Microsoft の Azure AI Search ドキュメントは、ベクトル検索では内容を数値で表すので、クエリのベクトルに最も近いものが一致し、「dog」と「canine」のように、言葉は違っても意味が近いものを見つけられる、と説明する。
- **出典**:
  - https://www.anthropic.com/news/contextual-retrieval （確認日 2026-10-16、本文確認済み）
  - https://docs.cloud.google.com/vertex-ai/docs/vector-search/overview （確認日 2026-10-16、本文確認済み）
  - https://learn.microsoft.com/en-us/azure/search/vector-search-overview （確認日 2026-10-16、本文確認済み。更新日 2026-08-05）
  - https://aws.amazon.com/what-is/vector-databases/ （確認日 2026-10-16、本文確認済み）
- **確度**: 高
- **出題の狙い**:
  - 問い方の案: 「RAGで使われるベクトルデータベースの役割として最も適切なものはどれ？」→ 「文書や質問を数値のベクトルにして保存し、意味の近いものを探し出す」。
  - 別案（場面型）: 「『犬』と入力したときに、『イヌ科の動物』『子犬』のような言葉は違っても意味が近い文書も見つけられるのは、どの仕組みによる？」→ ベクトル（意味の近さ）検索。
  - 紛らわしい誤答候補: 「キーワードが完全に一致する文書だけを探す」（従来のキーワード検索の説明）、「生成AIの回答を人間の言葉に翻訳する」「モデルの重みを保存する」（学習済みモデルとデータの保存先を混同させる）、「画像を高解像度にする」。
  - 注意:
    - 「ベクトル検索はキーワード検索より常に優れる」「キーワード検索は使えない」とは言わない。AWS と Microsoft はハイブリッド検索（キーワードとベクトルの併用）を紹介しており、併用すると良い結果になることが多いとも述べる。
    - 製品名（Azure AI Search、Vertex AI など）は問題・解説に入れない。
    - g3-03 は「埋め込み＝意味をベクトルに変換する処理」、g3-11 は「チャンク」。この問題は「保存先・検索のしかた」を問うので別の角度だが、選択肢に「埋め込み」を入れる場合は g3-03 との混同を避ける（誤答ではなく別の用語として入れるなら、解説で処理と保存先の違いを示す）。
    - k8-04（コサイン類似度）は G検定の数式的な類似度の問題。生成AIパスポートでは類似度の計算方法を問わない。
